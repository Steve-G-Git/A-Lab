01
INFRASTRUCTURE LAB  ·  LINUX OPERATIONS  ·  VERSION 1 COMPLETE
LeanOps Lab
Problem: A fictional small-business server began with unnecessary exposure, changing network addresses, weak administrative controls, no repeatable monitoring, and no tested recovery process.
What I configured
I built the Ubuntu Server VM and its NAT and isolated host-only networks, then configured static addressing, key-only SSH, UFW, systemd monitoring, Bash and Python automation, SMTP alerts, Samba access groups, and two backup processes.
Testing and proof
I closed thirteen PDCA cycles using reboot-persistence checks, Nmap scans, allowed and denied share-access tests, controlled failures, rollback tests, isolated restores, email-delivery tests, and SHA-256 comparisons from both Ubuntu and Windows.
Problem and correction
The original VirtualBox DHCP service was on the wrong subnet, and a later systemd sandbox blocked UFW's runtime lock. I corrected the subnet and isolated the sandbox failure before changing ProtectSystem from strict to full.
What I would improve next
The strongest next cycle would add encrypted, versioned off-site backup or centralized identity, but only after defining an observed problem, success criteria, validation, and rollback.

02
INTERACTIVE STUDY APPLICATION  ·  REACT  ·  LIVE
OSI Explorer
Problem: The OSI model is often taught as seven isolated boxes, which makes it difficult to see how protocols, addressing, devices, commands, and troubleshooting evidence connect.
What I built
I built a React and Vite application with seven layer pages, a searchable topic encyclopedia, a connected knowledge map, and a guided twelve-step packet journey. Reusable data files and stable topic IDs keep the learning content separate from the interface.
Testing and proof
I ran the Vite production build and preview, checked routed navigation, desktop and mobile layouts, keyboard focus, and reduced-motion behavior, then verified the automated GitHub Pages deployment and live site.
Problem and correction
I worked through npm, lockfile, Vite, Git, and GitHub Actions deployment failures. Correcting the Vite base path to /osi-explorer/ and standardizing the deployment workflow produced a repeatable live build.
What I would improve next
Add automated integrity checks for topic IDs and connections, practical troubleshooting scenarios, and more protocol diagrams while continuing mobile and accessibility testing.

BROWSER STUDY TOOL  ·  VANILLA JAVASCRIPT  ·  LIVE
IT Support Lab Terminal
Problem: Static notes made it easy to reread technical facts without actively recalling them or practicing command-oriented navigation.
What I built
I built the terminal interface, keyboard input handling, command registry, topic navigation, randomized quiz engine, accepted-answer matching, session scoring, and XP tracking with HTML, CSS, and vanilla JavaScript.
Testing and proof
The source implements command lookup, tab navigation, quiz start and answer handling, score and XP updates, and unknown-command feedback. Automated portfolio checks validate page destinations and JavaScript syntax.

Move the study content out of the interface file, add automated tests for every command and accepted answer, and add progress persistence only if the tool continues to be useful.

BROWSER STUDY TOOL  ·  TROUBLESHOOTING PRACTICE  ·  LIVE
Network Troubleshooter
Problem: Memorizing the troubleshooting process does not provide practice choosing the next action from incomplete evidence or explaining why another action is premature.
What I built
I built a state-driven scenario engine with four network incidents, staged evidence, multiple-choice decisions, progress tracking, and separate explanatory feedback for correct and incorrect choices.
Testing and proof
The source contains four complete scenarios covering APIPA and DHCP, WAN failure, a physical loop, and switch security. Each step defines choices, a correct path, and explanatory feedback; automated checks validate page destinations and JavaScript syntax.
Problem and correction
The content audit exposed stale certification branding and a WAN scenario that incorrectly kept DNS in scope after a numeric external IP test failed. I removed the branding, corrected the WAN diagnosis, and strengthened the broadcast-storm evidence.
What I would improve next
Add more support scenarios, vary addresses and symptoms between sessions, and create automated path tests so every branch and explanation is checked after future edits.

05
TECHNICAL CASE STUDY  ·  FIRMWARE RECOVERY
Neptune 4 Plus MCU Recovery
Problem: After a failed firmware update, the Klipper interface still loaded but temperature readings, motors, heaters, and communication with the printer MCU were lost.
What I investigated
This is a real repair case study, not a software project. I separated the Linux host, CH340 USB serial interface, COM port, UART connection, and MCU firmware layers, then used Device Manager, vendor firmware, a microSD recovery attempt, and STM32CubeProgrammer.
Testing and proof
The recovered printer cleared the Klipper error, restored live temperature readings, and regained motor and heater control without replacing hardware or reinstalling the host system.
Problem and correction
The standard SD-card restore completed but left the same error, and the first direct UART attempt failed with a boot-mode error. Those failures ruled out a host repair and focused recovery on restoring a valid MCU firmware state.
What I would improve next
Capture screenshots and logs during the incident, record exact firmware versions and recovery commands, and create a concise repeatable rollback procedure. The current case study clearly discloses that screenshots were not captured.
